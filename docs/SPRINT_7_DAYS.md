# خطة تحدي 7 أيام باستخدام Codex (هدف طموح وغير مضمون)

هدفها **تسريع الوصول إلى أول مسار عامل ببيانات اصطناعية**، مع عدم تخطي الأمان أو اعتبار جميع متطلبات SRS مكتملة دون اختبار.

| اليوم | حزمة العمل | الإنجاز المقصود | حاجز الجودة |
|---|---|---|---|
| 1 | FND-01, FND-02, DB-01, SEC-01 | مشروع Flutter/API وقاعدة بيانات وعقود مستقرة وCI | auth عزل مستخدمين وفشل وصول غير مخوّل |
| 2 | FND-03, STU-01, STU-02, ASM-01 | RTL والملفات المجهّلة وقوالب البطاقات الست | لا حقل اسم/ميلاد/صحة؛ قوالب ثابتة |
| 3 | ASM-02, AI-01, AI-02 | حفظ تقييم واعتماده، توليد خطة مسودة ومراجعتها | لا توليد قبل الموافقة والاعتماد، ولا تشخيص |
| 4 | ACT-01, SES-01, PRO-01 | الأنشطة، الجلسات، النسب، الرسم | حسابات صحيحة + حالة غياب + ارتباط بهدف معتمد |
| 5 | OFF-01, OFF-02, RPT-01 | تخزين مشفر، مزامنة، PDF/DOCX | اختبارات تكرار وتعارض، طباعة عربية |
| 6 | QA-01, QA-02, QA-03 | تكامل ومقارنة Android/iOS وتجارب قطع الشبكة | سجل فحص حقيقي + ما لم يُختبر يُعلّم BLOCKED |
| 7 | REL-01, REL-02 + إصلاحات | Builds تجريبية وتوثيق Known Issues | لا إطلاق/بيانات حقيقية قبل حسم قرارات البيانات |

## توزيع الجلسات
- يوم 1: **منسق واحد** لتأسيس العقود؛ يمكن فتح عامل لتصميم واجهات مستقلة بعد تثبيت التصميم.
- أيام 2–4: 2–4 جلسات متوازية حسب قدرة التشغيل (تقييم، واجهات، API، أنشطة/جلسات) مع PRs صغيرة.
- أيام 5–7: جلسة للمزامنة وأخرى للتقارير وأخرى للاختبار والتكامل؛ لا تخلط تعديل schema في فروع متفرقة.
- بطاقات التقييم والمخرجات بحاجة لمراجعة مختصة تربوية؛ لا يقوم CI مكانها.

## تعريف النتيجة
- **نموذج برمجي أولي** = شاشات وربط API حقيقي مع بيانات اصطناعية واختبارات أساسية، قد يكون ناقصًا أو محجوبًا عن الاستخدام الفعلي.
- **MVP صالح للتجربة الميدانية** = اجتياز حالات الاستلام المبينة في `docs/TEST_PLAN.md` على Android وiOS مع حماية المعلومات ودعم عدم الاتصال.
- **جاهز للنشر** = ما سبق + استيفاء المتجرين وسياسات البيانات وحسابات التوقيع والمراجعات الخارجية؛ قد يتجاوز هذا السبعة أيام.
