# طريقة تشغيل Codex — رسائل جاهزة للنسخ

## 0) قبل أول جلسة
- افتح مجلد الحزمة كمستودع العمل؛ لا تبدأ من نسخة ZIP أو مستند فقط.
- جهّز Git + Flutter + Android SDK، وخطة للوصول إلى macOS/Xcode للاختبار والبناء على iOS، وNode.js وPostgreSQL.
- لا تدخل مفاتيح API في prompt أو المصدر أو ملفات الالتزام. أنشئ بيئة تطوير محلية من `.env.example` عندما ينشئها Codex.
- راجع `docs/OPEN_DECISIONS.md`: ما يعتمد على سياسة البيانات/الموافقة يبقى في وضع تجريبي باستخدام بيانات اصطناعية.

## 1) رسالة المنسق الرئيسية (Codex في جذر المستودع)

```text
أنت منسّق تطوير تطبيق خطوة (Khotwa) وفق وثيقة SRS v1.3.
اقرأ AGENTS.md وTASKS.md وdocs/requirements_map.json وdocs/ARCHITECTURE.md وdocs/OPEN_DECISIONS.md وdocs/TEST_PLAN.md كاملة.
ابدأ بتقييم حالة المستودع الحالية دون افتراض أن التطبيق موجود. تأكد من عدم وجود تعارضات غير محفوظة.
نفّذ المهام غير المنجزة ذات الأولوية وفق التبعيات: FND-01 ثم FND-02 وDB-01، ثم بقية Wave 1.
اكتب الكود الحقيقي والاختبارات والهجرات والتوثيق، لا mock UI على أنها ميزات مكتملة.
لا تدخل بيانات حقيقية، ولا ترسلها إلى مزوّد AI، ولا تنشر للمتاجر قبل حسم القرارات اللازمة.
قسّم المهمة إلى PRs صغيرة وفروع مستقلة؛ لا تُعدّل main مباشرة ولا force push.
بعد كل مهمة: شغّل اختبارات مناسبة فعليًا، صحّح الأخطاء، أبلغ نتائج دقيقة، حدّث TASKS.md وdocs/PROJECT_STATUS.md وبيانات التتبّع.
لا تزعم أن Android وiOS تم اختبارهُما دون سجلات تشغيل فعلية على كل نظام.
اعرض الآن خطة التنفيذ للدفعة الأولى، ثم ابدأ التنفيذ مباشرة إذا الأدوات متاحة.
```

## 2) رسالة عامل مستقلة (لكل worktree)

```text
اقرأ AGENTS.md وTASKS.md وdocs/PARALLEL_WORK.md والمتطلبات المرتبطة بمهمتك.
مهمتك: <TASK_ID> — <TASK_TITLE>.
تملّك فقط المسارات المحددة لك في docs/PARALLEL_WORK.md.
تأكد أن عقود API المتفق عليها موجودة؛ إذا لم تكن، حضّر PR تعاقدًا منفصلًا قبل التنفيذ.
أنشئ الفرع feat/<task-id>-short-name داخل worktree الخاص بك.
نفّذ الوظيفة واختبارات النجاح والفشل وحالات الخصوصية، ثم شغّل فحوص الوحدة المناسبة.
لا تغيّر مخطط بيانات/عقود مشتركة دون التنسيق مع المنسق. لا تُدمج main بنفسك.
اختم بتقرير: FRs، ملفات، أوامر اختبارات ونتائج، SHA إن وجد، معوقات.
```

## 3) رسالة مراجعة صارمة قبل دمج PR

```text
راجع التغييرات في هذا الفرع مقارنة بـ main: هل تغطي المتطلبات المربوطة في docs/requirements_map.json؟
افحص ملكية الملفات، التشفير الفعلي، عزل الحسابات، سجلات البيانات، مسار إقرار الموافقة، منع التشخيص والتوليد دون اعتماد، التعارضات والتكرار أثناء المزامنة.
شغّل الاختبارات وأعطني حالات إعادة إنتاج الأخطاء. لا تعطِ موافقة نظرية لأي مسار غير مختبر.
إذا لا توجد بيئة iOS/Android، اذكر صراحة أن فحوص هذه المنصة غير متحققة.
```

## 4) رسالة إعادة بناء حالة المشروع بعد انقطاع العمل

```text
افحص git status وgit log وPRs المتاحة وTASKS.md وdocs/PROJECT_STATUS.md؛ لا تفترض نجاح أي مهمة غير موثّقة.
تحقق من الفروع المتاحة وحدد المهمة غير المكتملة ذات الأولوية والتي لا تضارب عملًا جاريًا في worktree آخر.
شغّل فحوص البيئة، وحدّث حالة التقدم بالأدلة، ثم تابع التنفيذ.
```

## 5) أوامر متكررة

```bash
python scripts/validate_planning.py
# بعد إنشاء backend/
cd backend && npm ci && npm run lint && npm run typecheck && npm run test:ci
# بعد إنشاء mobile/
cd mobile && flutter pub get && dart format --output=none --set-exit-if-changed . && flutter analyze && flutter test
# بناء Android على بيئة مجهزة
cd mobile && flutter build apk --debug
# iOS على macOS/Xcode فقط
cd mobile && flutter build ios --debug --no-codesign
```

## 6) أين تضع لقطات الاختبار؟
- احفظ **نتائج مختصرة فقط** في `docs/PROJECT_STATUS.md` وداخل PR؛ لا تحفظ dumps لقواعد حقيقية أو صور شاشة تحتوي معلومات طفل.
- لا تضع الأسرار أو محتويات `.env` في المحادثات أو المخرجات.
- `docs/SPRINT_7_DAYS.md` خطة تسريع لا تستبدل معايير الاستلام.
