# MVP contract extension — 2026-11-11 (acceptance in progress)

Existing student snapshots remain readable. Student adds `gender:male|female|unspecified`, `referralReason`, `classroomObservation`, `difficulties`, `familyNotes`, `teacherNotes`, `proposedDurationWeeks`, `sessionsPerWeek`, `sessionMinutes`; defaults preserve existing records. Free text requires privacy review and is never automatically sent to AI.

Before AI skills/preview/generate, FR22/32 require an explicitly completed `gender:male|female` and nonempty `referralReason`, in addition to grade/age and approved educational evidence. Missing/legacy/unspecified values remain saveable but return409 `STUDENT_INPUTS_INCOMPLETE` for AI; the user edits and syncs the student rather than the application inferring values. These basic fields are bound into the signed source digest and rechecked before/after generation; gender/referral prose are not in the provider payload.

Academic assessment1.1 adds optional `assessedOn:YYYY-MM-DD` and `gradeAtAssessment` (existing school-grade enum). New records snapshot these on creation; existing records cannot change them or acquire missing legacy values. Each item may contain optional `structuredObservations` with fields `pencilGrip`, `writingDirection`, `letterDots`, `taaForms`, `tanween`, `spellingNotes` on writing items2a/2b/5a/5b and `solutionMethod` on mathematics3*/6*. Each text is at most1000 characters and passes educational/privacy validation. These are descriptive evidence, not scores, diagnoses or AI inputs. Unfinished item/summary drafts are keyed by assessment/item and stored separately from saved records/outbox, with a fresh privacy confirmation at explicit save.

Custom initial-assessment skill labels need explicit `customSkillsReviewed:true` before preview and `customLabelsConfirmed:true` after preview when included. Server derives bounded reviewed labels from approved evidence; clients cannot invent a `reviewedLabel`. No consent flag is cached. Plan `presentation.studentReference` is rendered locally as الطالب/الطالبة and does not change the goal criteria or tools.

Gemini uses a small provider-only JSON decoding schema; the original complete Zod schema and server safety rules still validate every result. Provider errors distinguish busy503, usage limit429, request400, configuration401/403 and transport failure. No automatic retry or fallback plan is introduced.

`initialAssessment` uses the normal encrypted snapshot/outbox envelope, parent=studentId. Data: `{id,studentId,createdAt,assessedOn,status:'draft'|'approved',method:'directObservation'|'educationalActivity'|'checklist'|'academicCards',academicAssessmentId:null|UUID,alternativeReason,domains:[{id,label,currentPerformance,strengths,needs,skills:[{id,label,level:'mastered'|'developing'|'needsSupport',evidence}]}],previousStrategies:[{name,result}],privacyReviewed:true,approvedAt:null|ISO}`. Approval is explicit and requires documented results and a development need. Academic evidence must reference an owned approved academic assessment. Approved results are immutable; reassessment creates a new record. Custom domains/skills are specialist-entered, never inferred or treated as clinical categories. Known catalog IDs can supply AI input; custom labels require a separately reviewed explicit flow before external processing.

`session` extends the validated `planning/domain.ts` session with `createdAt`, `activityId:null|UUID`, `notes`, `privacyReviewed:true`. Parent=studentId. It references the owned approved plan record and an existing goal; an optional activity must match the same student, plan and goal. Performed sessions require valid trials, support and engagement. Absent/cancelled sessions have null performance fields. No future performance, and no use of assessment scores as intervention accuracy. Offline batch writes are durable before sync.

`POST /v1/plans/:id/versions` accepts `{revision,operationId,confirmed:true,content,templateOptions?}` and returns `{record}` for a new specialist draft. It preserves the previous approved record and source history. Retries reuse an operation ID. Optional template flags are `showStrategies`, `showRecommendations`, `showSessionSchedule`; goals and core content remain required.

Specialized server-owned kinds `activity`, `activityTools`, `institutionProfile`, `reportExport` remain unavailable for generic sync upserts. They use owner-isolated read/sync pull and dedicated validated write routes.

Activity routes provide saved tool settings, a signed exact educational payload preview, explicit generate confirmation and operation receipt, and human review of a suggested draft associated with an approved goal. The payload excludes student/account IDs, code, raw assessments and demographic dates. Grade is an explicit controlled activity input in SRS FR-56. Provider failure creates no fallback content. Custom tool labels and goal prose are visible in the exact preview and require privacy review before confirmation.

Reports: `GET/PUT /v1/reports/settings`, `GET /v1/reports/exports`, `POST /v1/reports/export` with `{studentId,planId,type:'progress'|'parent'|'administration'|'plan',periodStart,periodEnd,format:'pdf'|'docx',includeGrade?:boolean}`. Export is a binary response with content disposition and report serial header. `POST /v1/reports/batch` with `{reports:[...],format}` produces separate files plus anonymous serial/code mapping in ZIP. Settings contain `{institutionTitle,logo:{mime,base64}|null,privacyReviewed:true}`. Default grade exclusion preserves the unresolved FR-22/89 conflict; an explicit per-export user choice can include it. Generated files must be inspected as real Arabic PDF/DOCX before claiming acceptance.
